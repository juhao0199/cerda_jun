## Access policy

- Owner can view all CRM records and assign a lead to one active application Staff account, reassign it, or unassign it. Assignment is a business operation, not an account privilege change: ordinary Owner session/MFA, CSRF and Origin validation apply, no fresh password/TOTP required. Team role changes still require step-up.
- Staff can list, search, read, transition and add notes only to assigned leads. Their overview, legacy inquiries endpoint and client directory are scoped, too. A linked client profile is shared by staff who have assigned leads linked to it; other leads and notes remain private. Conversion uses the existing email deduplication policy, so a newly linked canonical client profile becomes visible to that staff member. Client application role has no CRM access.
- All existing and new unassigned leads are Owner-only. No auto-assignment. Existing data preserved. No cross-tenant model or PostgreSQL RLS; enforcement is at application API level.
- Disabled/demoted accounts cannot access CRM, but assignments remain stored. If restored to active Staff, assignments become accessible again. Owner can explicitly reassign/unassign. A reassignment denies subsequent unauthorized API requests, but cannot retract already delivered data or cancel in-flight reads. UI refreshes after writes; no real-time push.
- `POST /api/v1/staff/crm/assign/` expects `reference` UUID string, numeric `version`, `assigneeId` positive account ID string or null. It checks current Owner role/session version, active target Staff, locks users/profiles in stable order then lead, uses the same CRM version and emits lead activity and security audit in one transaction. Unauthorized lead reads/writes by Staff return 404. No-op assignment does not increment version or emit audit.
