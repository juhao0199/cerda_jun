# V1.9.3 — Media library and optional private S3 storage

Apply to V1.9.2.1, after committing/merging that release. Backup PostgreSQL before applying. Rebuild backend (boto3 dependency), run `makemigrations --check --dry-run`, migrate and check. No new npm dependencies. Run `test apps.accounts apps.inquiries apps.quotations apps.blog`, frontend test/typecheck/build, then `npm --prefix frontend run test:e2e -- blog.spec.ts media.spec.ts --workers=1`.

## Media library
- `/workspace/media`: Owner/Staff list, search, preview, upload, edit default metadata, crop/rotate to a new immutable copy. Owner-only removal, checked against current drafts, published snapshots and every stored historical revision. The image row is locked during article save/publication and deletion; default Django PostgreSQL READ COMMITTED isolation is assumed.
- Choose existing images in cover settings or the body toolbar. Article image alt/caption are independent snapshots; library metadata is a reusable default for inline images. Changing metadata does not rewrite previous articles. Cover alt remains decorative in this release.
- Batch selection/drop: up to five files, processed sequentially; if a later file fails, earlier uploads are retained. Existing per-account/IP upload limit (5 attempts per 5-minute bucket) also applies to derived copies. Max 5 MB input, 16 MP, output JPEG up to 1600 px / 2 MB. Crop presets use a centered crop; no freeform crop handles. Existing images retain IDs, bytes and article links. Legacy filenames are unknown and default to image.jpg; dimensions and actual stored byte count are preserved.
- Usage details show up to 100 current article slugs, with total current article and revision counts. The displayed byte total is logical processed image size, not physical DB or S3 billed storage. A historical reference blocks deletion even after the current article changes.
- Metadata edits use version checks; binary bytes never change. No public bucket links; public image delivery still checks current published article references. All historical/unused media stays private.

## Object storage (optional; default is unchanged PostgreSQL)
No MinIO container is started or bucket created automatically. To enable an existing private S3-compatible bucket, create the bucket outside this app, enforce no public access, HTTPS with trusted certificates, least-privilege credentials scoped to the `blog/images/` prefix (GetObject and PutObject), and backups/versioning. Do not put secrets in Git. The optional settings (development `.env` via Compose env_file, production `.env.production` via optional overlay):

```
BLOG_OBJECT_STORAGE=s3
BLOG_S3_BUCKET=your-private-bucket
BLOG_S3_REGION=us-east-1
# Omit endpoint for AWS S3; for S3-compatible storage set its real HTTPS endpoint.
BLOG_S3_ENDPOINT=https://your-private-storage.example
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
```

New uploads are written to S3 and read back to verify before saving the DB metadata; the DB binary is empty for those new uploads. A storage error returns 503 and does not commit an asset record. A DB commit failure after S3 upload can leave a private orphan. Existing DB bytes are still served without contacting S3. The application does not expose presigned URLs. For production explicitly use the overlay (which adds a separate egress network to backend/migrator, not DB/frontend):

```
docker compose --env-file .env.production -f compose.prod.yaml -f compose.s3.yaml up -d --build
```

Use the same files and configuration for subsequent deploys. Do not switch bucket/prefix or disable credentials while any S3-only assets exist. Database backups alone are insufficient after enabling S3; back up both stores. The production migration service applies updated runtime-grants.sql; metadata UPDATE columns and DELETE are now granted for app-controlled deletion. This is application-level authorization, not a database-level reference constraint.

Optional existing asset copy (read/write credentials required, run under migrator or development DB owner):

```
python manage.py copy_blog_images_to_s3
python manage.py copy_blog_images_to_s3 --apply
```

In local Docker use `docker compose exec backend python manage.py ...`. In production use `docker compose --env-file .env.production -f compose.prod.yaml -f compose.s3.yaml run --rm migrate python manage.py ...`. Copy verifies bytes and retains DB copies, so it does not reclaim DB space. It is restartable and does not change article references. Object mode is optional, not live-tested here. App deletion removes an unreferenced asset row but intentionally does NOT delete a remote object inside a DB transaction; private orphan objects require separately audited operator cleanup after checking live DB references and backup retention. No automatic garbage collection or freeform crop UI yet. Never run unconditional bucket lifecycle expiration on live objects.

Rollback: restore the pre-upgrade DB backup if necessary, and restore corresponding object data if used. Git revert alone does not restore deleted images or S3-only blobs. Do not downgrade after new S3-only images have been uploaded unless exported/restored to PostgreSQL.
