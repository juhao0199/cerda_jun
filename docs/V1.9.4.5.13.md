# V1.9.4.5.13 — Competitor Intelligence Engine

Applies to the competitor module delivered in V1.9.4.5, including the public-site releases through V1.9.4.5.12. No changes to marketing/3D/motion or to existing paired AI observations. No Search Console integration or paid APIs.

## Development

Apply the patch on a separate branch, back up PostgreSQL, rebuild backend, run `makemigrations --check --dry-run`, `migrate`, `check`. Migration `blog.0010_competitor_intelligence` adds an append-only report table and a versioned relationship field. Existing competitors remain unclassified until explicitly classified. Open `/workspace/competitors`, select Open benchmark, then Open website intelligence. Owner can classify and run a scan; staff can review reports and compare topics. Select apex or www explicitly; a canonical robots.txt redirect to the other registered hostname is permitted, and the scan then samples only that destination. Page redirects are not followed. For Attio, use Reference brand if it is a design reference rather than a direct commercial competitor.

## Scanner boundaries

No arbitrary URL input, no cookies, no login, no Javascript, no images, no HEAD/POST or external link traversal. The input is an existing registered competitor ID and a fixed apex/www variant. DNS is absolute and every resolved address must be public; TLS uses the registered hostname for certificate validation and SNI, with a pinned numeric public IPv4 address for the socket. No HTTP proxy; only a canonical HTTPS robots.txt redirect to the other registered hostname is permitted. A global database advisory lock and existing DB rate limiter allow at most five scan attempts in a five-minute fixed window. A scan is capped at 22 seconds of network budget, 10 requests, five HTML page attempts, two XML sitemap documents, 1 MiB per response, and at least one second between request starts. Oversized/unsupported responses and inaccessible robots are incomplete, not successful. Robots rules support exact product token groups, wildcard/default rules, longest matching allow/disallow, crawl delay up to three seconds; ambiguous selected rules fail closed. This is a conservative subset, not a fully general RFC 9309 implementation. Root directives for other bots are estimates from parsed rules only; actual access can differ. Unsafe robots redirects, loops, and 401/403/429/503 stop the crawl. Reports include HTTP status or the failing network stage. A canonical redirect is counted against the original request/time budget and revalidated by DNS pinning and TLS. No attempts to bypass a block. HTML parsing is heuristic (not rendered DOM) and bounded; signals are not real SEO ranks, AI citations, authority, or traffic. Technology signatures do not identify a full stack.

## Data and comparison

Reports store titles/headings, metadata, signal results and aggregate counts, not full remote HTML, and are private/append-only. Comparison matches phrases against sampled competitor HTML title/headings and up to 200 currently published blog title/headings, with separate full-text blog counts. This does not compare full public websites and misses synonyms, dynamic JS and static homepage sections. Use actual evidence to prepare a private content opportunity manually; existing paired observation requirements remain unchanged. No automatic draft publishing.

## Production safety

External scanning defaults to disabled outside DEBUG. The optional `compose.intelligence.yaml` overlay adds outbound network connectivity to the backend; **do not enable it until outbound firewall rules deny internal, loopback, link-local, metadata, private and non-public destinations**, permit only required DNS and HTTPS, and the deployment owner has reviewed egress routing. For production use `docker compose -f compose.prod.yaml -f compose.intelligence.yaml ...` only after this review; otherwise leave disabled. Runtime grants must be reapplied after migration. DNS/IP validation is defense in depth, not a substitute for network isolation. Website audit sends normal identifiable public HTTP GET traffic; respect terms of service and site restrictions. No scheduled crawling.

## DNS budget hotfix

DNS waits up to five seconds, and each HTTPS request has a nine-second ceiling, both bounded by the original 22-second scan deadline. Absolute DNS names, the two resolver slots, public-IP validation, address pinning, TLS verification and robots rules remain unchanged. If DNS still times out, diagnose the Docker Desktop resolver and host connectivity before retrying. Do not enable the production egress overlay as a DNS workaround.

## Per-scan DNS reuse

Within a scan, reuse only the validated public IPv4 for the exact hostname. A canonical hostname change requires its own DNS validation. The cache is discarded after each scan. TLS still verifies the hostname per connection; the original request count, deadline, robots policy and rate limits are unchanged.
