# V1.9.4.2 — Independent SEO, AEO & GEO workspaces

Base: V1.9.4.1, with the V1.9.3 hotfixes. No new pip/npm dependencies. Apply the incremental patch before building. The runtime migration is `blog.0006_discovery_observation`.

## Workspaces
- `/workspace/seo`: dashboard with actual inventory counts, separate SEO editor, search/social previews, indexing and metadata checks.
- `/workspace/aeo`: dashboard and manually recorded answer observations, dedicated direct-answer/Q&A/source editor.
- `/workspace/geo`: dashboard and manually recorded brand/citation observations, dedicated factual claim/context/reference editor and structural citation-readiness checks.
- Dashboard metrics for provider data remain unavailable until a real provider is integrated. Manual records are per observation (not unique prompts, impressions, citation rates or rankings).
- Site inventory lists actual static routes, but these routes are source-managed. Only blog posts can be changed by these editors. Manual observations can target the home page, blog index, privacy page or a current blog article. No outbound requests or scraping.

## Shared content and safety
Editors use the same versioned private article draft and existing save endpoint. They preserve other fields and rich nodes; save rejects stale versions. Owner-only publication remains in Blog CMS. Do not publish unverified evidence. The GEO checklist is heuristic, not a fact check or citation prediction. Observation records are append-only, with a required user-supplied evidence/context note; they are accessible only to authenticated owner/staff and have separate aggregate counts for AEO and GEO. The recorded timestamp is entry time, not independently verified search time. Include the actual search time and region in the evidence note. Do not record private user data. GEO observations group brand/citation outcomes; provider-specific automatic tracking and separately quantified mentions/citations are not implemented.

## Upgrade
1. Confirm V1.9.4.1 has been applied; back up PostgreSQL.
2. `git apply --check <patch>` then `git apply <patch>`.
3. `docker compose up -d --build backend`; `docker compose exec backend python manage.py makemigrations --check --dry-run`; `docker compose exec backend python manage.py migrate`; `docker compose exec backend python manage.py check`.
4. Restart Next.js. In production, apply the existing deployment workflow for migrations and updated `infrastructure/postgres/runtime-grants.sql` (as migrator), and rebuild/reload Nginx with the new allowlist. No public endpoint is added.
5. Run `docker compose exec backend python manage.py test apps.accounts apps.inquiries apps.quotations apps.blog --verbosity=2` and `npm --prefix frontend test`, `npm --prefix frontend run typecheck`, `npm --prefix frontend run build`, `npm --prefix frontend run test:e2e -- blog.spec.ts media.spec.ts editorial.spec.ts --workers=1`.
