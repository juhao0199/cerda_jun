# V1.9.1 — Blog CMS

Apply this incremental patch to V1.9.0 (including the logo hotfix). No npm or Python dependencies added. The existing three static articles are copied verbatim (title, summary, category, headings and paragraphs) into the database by `blog.0002_seed_existing`. Their slugs remain unchanged. Import time is the initial published timestamp; the original static content had no dates. Reading time is recalculated from text. Migration rollback of the seed is intentionally a no-op to avoid deleting edited articles; do not roll back schema without backing up data.

## Update

From project root, create or switch to `feature/v1.9.1-blog-cms`, back up PostgreSQL, then run `git apply --check` and `git apply` with the patch. Rebuild the backend and run `makemigrations --check --dry-run`, `migrate`, and `check`. Start Next.js as usual. Do not replace `.env` or database volumes.

- `docker compose exec backend python manage.py test apps.accounts apps.inquiries apps.quotations apps.blog --verbosity=2`
- `npm --prefix frontend test && npm --prefix frontend run typecheck && npm --prefix frontend run build`
- `npm --prefix frontend run test:e2e -- blog.spec.ts --workers=1`

The new browser tests mock API responses; the Django tests verify real database publishing and permission logic. For a real public smoke test with backend and frontend running, open `/blog`, `/blog/business-website-budget`, `/sitemap.xml`, `/rss.xml`, `/robots.txt`. Create a unique test draft, confirm its public URL returns 404 and it is absent from the sitemap/feed; publish as Owner, confirm it appears, edit it without publishing and confirm the old public content remains; archive and confirm it disappears, restore and confirm it stays private until re-published. Staff can create/edit drafts but cannot publish, archive or restore. Client role has no CMS access. Public pages fetch only published snapshots directly from Django; there is no static fallback that could resurrect archived content. The home page degrades with an unavailable notice if the blog API fails. The blog detail/list fail rather than serving misleading data if Django is unavailable. The production site is no-store and server rendered; previously downloaded data cannot be recalled.

## Editorial behavior

The permanent slug is chosen on creation and cannot be changed (no redirect manager yet). A post contains an editable draft and independent published snapshot. Publish copies the saved draft to the public snapshot; the public timestamp is the current publication time. Archive removes the public snapshot while retaining draft and history; restore returns to private draft. Latest 100 revisions can be previewed by staff and owner; history is retained and not editable through APIs. Staff can edit all non-archived editorial drafts, unlike CRM's assigned-record scope. Save first before publishing. Conflict 409 preserves unsaved form contents; reload after reviewing. No automatic deletion. Public pages and preview render headings/paragraphs as text; this is a block editor, not arbitrary HTML or a WYSIWYG rich text editor. Each request is capped at 23 KB; article section text is limited to 17 KB UTF-8, 20 blocks, 10 tags. Three local SVG cover presets, no uploads or remote URLs. SVG Open Graph support depends on social platform. No scheduled publishing, custom canonical override, public category index, or media library yet. RSS shows up to 20 newest publications; sitemap covers paginated public posts up to 24,000 entries. The `blog` category is available in Security Center.

## Deployment notes

Set `SITE_URL` in frontend `.env.local` for local canonical links (defaults to `http://localhost:3000`). `BACKEND_URL` defaults to `http://127.0.0.1:8000`. In production the updated `compose.prod.yaml` attaches the frontend to the private API network (not the database network) and sets `BACKEND_URL=http://backend:8000`, `SITE_URL` and `BLOG_BACKEND_ORIGIN` from `SITE_ORIGIN`. Direct public-only fetches use the configured backend origin as Host/proto, with no cookies or forwarded user headers; ensure it is allowed in Django. Frontend now has network access to the backend; review this trusted service boundary before deployment. Nginx exposes only the enumerated staff CMS endpoints; public articles are rendered server-side, public API need not be exposed by Nginx. Reapply runtime grants after migration to prevent UPDATE/DELETE of revision records. Production TLS, grants, network and end-to-end behavior require deployment-specific verification.
