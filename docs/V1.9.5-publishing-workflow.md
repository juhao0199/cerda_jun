# V1.9.5 — Publishing Workflow & Editorial Calendar

Requires V1.9.4.6.1. Apply migrations and runtime grants before enabling production. No new dependencies.

- `/workspace/calendar`: submit saved unpublished articles (including updates) or the website draft; queue, owner review/return, notes, schedule and immediate publishing, UTC month grid and mobile agenda. Published calendar entries use actual publication time. Each workflow event is retained, with latest 50 shown in plan details.
- Staff/owner submit and resubmit; owner approves, requests changes, schedules, or publishes; owner or current submitter cancels. An active workflow blocks direct publication until cancelled or released through calendar. Content not enrolled retains its existing direct-publish path. Saving/renaming/archiving a draft changes its version and invalidates approval; old public content stays visible except explicit archive.
- Owner should open saved content for review before approval. Approval binds the target version; scheduling also binds the current owner's account security version. Scheduled runner rechecks authorization and content version under transaction locks. Expired/revoked scheduling authorization or changed content blocks release; re-review is required. No external calls; existing publication and audit functions used. No automated reviewer, email or notifications.
- Dates explicitly UTC. For Bangkok 19:00 UTC+7 enter 12:00 UTC. Future releases allowed up to 365 days. Calendar shows up to 200 entries per month and paginated queue. The current title in the queue is not an immutable historical title; actual published revisions remain in CMS history.
- Migration `blog.0012_publishing_workflow`. Back up DB. Reapply `infrastructure/postgres/runtime-grants.sql` after migration in production.
- Test one tick: `docker compose exec -T backend python manage.py publish_due_content`. To enable a foreground runner in a separate terminal: `docker compose exec -T backend python manage.py publish_due_content --watch`. Checks every 60 seconds plus execution time; stops if terminal/container stops or a fatal DB error occurs. In production run supervised or invoke the one-shot command every minute through the deployment scheduler. Do not enable unattended publishing until integration tests and authorization checks pass. No runner is started automatically; overdue plans remain queued and are checked when runner resumes. Max 20 due items per tick; no guarantee of exact second delivery. Manual publish still works without runner.
- `python manage.py test apps.blog.test_publishing apps.blog.test_publishing_rules` and frontend `npm test`, `npm run typecheck`, `npm run build`, `npm run test:e2e -- publishing.spec.ts --workers=1`.
